# くらしのしるし — 生活の基盤プロダクト原則と再発防止

最終更新: 2026-08-09

## 0. このアプリの目的（最優先）

**「生活の基盤をこれ一つで支える」**。

家計簿、タスク管理（一日の予定と優先順位）、習慣づけ、メンタルヘルス、自己分析、自己管理を、一つの生活の流れとして扱う。機能を増やすこと自体は目的ではない。迷わず、少ない操作で、忙しい日にも続けられることを優先する。

## 1. 導線の原則

1. 入口では目的を三つに絞る: **記録する / 今日を整える / 見える化する**。
2. 目的を選んだ後は、必要な対象だけを選び、最終画面は一つの役割に集中させる。
3. 同じ情報を複数画面で編集させない。記録・見通し・分析の役割を分ける。
4. 説明を読まないと使えない項目は作らない。省略しても意味が残る場合は省略する。
5. ホームはハブであり、数値を詰め込む場所ではない。

## 2. 継続できる入力設計

- 歩数・睡眠は、忙しい日にコピーや手入力が負担になって記録が途切れないよう、iPhoneショートカット／同期を使った自動取り込みを優先する。
- 手入力が必要なものは、金額 → 方法 → カテゴリーのように自然な視線順で一度に終えられるようにする。
- 「毎日の習慣」はチェックリストだけに閉じず、必要なら**一日の流れの時間軸へ毎日繰り返す予定として配置**できるようにする。
- アイデアと目標は、テキスト専用の長いフォームではなく、画像・短いメモ・今月の目標を同じ紙面に置く端末内フリーボードとして扱う。

## 3. 情報の表示状態

- 金額の表示／非表示は、ページの役割ごとに分離する。
  - `支出・収入を記録`: `ui.moneyVisible`
  - `お金の見通し`: `ui.moneyOutlookVisible`
- 一方を隠しても、もう一方の表示状態を変えてはいけない。
- ローカルに残っている既存データを消さず、古い保存データには `normalize()` で不足キーを補う。

## 4. 共通部品の配置契約

### 枠の中のアイコン・文字

- 枠内の要素は `display:grid; place-items:center` または `display:flex; align-items:center; justify-content:center` で中央を決める。
- **文字のベースライン、行高、余白、疑似要素の translate に依存して中心を合わせない。**
- ×、＋、矢印なども文字記号ではなく、共通SVGアイコンを使う。丸枠の×はSVGを同じグリッドに置く。
- アイコンと文字を横並びにする部品は、共通 `gap` を持つ部品クラスにまとめ、画面ごとの個別微調整を禁止する。

### 数字・金額

- 基本文字は縦横比を崩さない（1:1）。
- 数字は `font-variant-numeric: tabular-nums` を検討し、同一系列の金額には同じ書体・ウェイトを使う。
- 通貨記号やマイナス記号は、数字との見た目を確認し、別フォント・別スケールで不自然にしない。

### 領域・余白

- 左でそろえるグループ、右でそろえるグループ、中央でそろえるグループを、画面ごとに先に決める。
- 背景は基本のドット紙を画面外への引っ張り時も切らさない。ページ背景だけでなく `html / body / app root` に同じ紙面を指定する。
- 共通の「ホームへ戻る」は、ホーム以外の全画面で同じ中央配置、アイコンと文字の近い間隔、同じ縦リズムを使う。

## 5. 繰り返し起きた不具合と再発防止

| 事象 | 原因 | 今後の対策 |
| --- | --- | --- |
| ×が丸の中心からずれた | 文字のベースラインと疑似要素の微調整に依存していた | SVGの`close`アイコンを中心グリッドへ置く。スクリーンショットでX/Y中心を確認する。 |
| 枠内のアイコン・文字がずれた | `line-height`とフォント固有の余白を配置基準にしていた | 共通部品はgrid/flex中心のみを許可し、個別のtranslateを増やさない。 |
| 記録の金額を隠すと見通しまで隠れた | 一つの表示フラグを複数ページが共有していた | 表示状態を機能単位に分け、設定キー名を明示する。 |
| ローカル確認とアプリ表示が一致しなかった | 確認用HTMLと実装CSS・実装JSが別系統だった | 実装確認は本番の`index.html`を同じローカルサーバーで開く。確認ページは仕様承認用に限定し、実装前に「確認用」と明記する。 |
| コードだけが表示された | HTMLをブラウザで開かず、テキストとして開いた | ユーザーに見せる前にローカルHTTP URLで実表示を確認する。コード内容をチャットだけで代替しない。 |

## 6. 実装・確認チェックリスト

### 変更前

- [ ] 変更対象を「共通部品」「画面固有」「データ状態」「表示確認」に分類したか
- [ ] 既存データを消さずに移行できるか
- [ ] 同じ役割の既存部品を再利用できるか

### ローカル表示確認

- [ ] 本番アプリと同じCSS・JSを読み込むHTTP表示で確認したか
- [ ] iPhone幅（390px前後）で、枠内の全アイコン・文字がX/Yとも中心に見えるか
- [ ] 上下に引っ張ったとき、紙面背景が途切れないか
- [ ] スクロール固定画面で、ホームへ戻る等の操作が画面外に出ないか
- [ ] 表示／非表示が他画面へ影響しないか

### 公開前

- [ ] 古いUI・古いイベント処理が残っていないか検索したか
- [ ] 表示用のバージョン、サービスワーカーのキャッシュ名、公開物が一致するか
- [ ] GitHub Pages公開後に実URLで確認し、PWAの更新手順を必要に応じて案内するか

## 7. ユーザーフィードバックの扱い

フィードバックは単発の座標修正として処理しない。問題が起きたら、

1. 原因を分類する（構造、共通部品、状態管理、CSS、確認不足）。
2. 共通ルールとして直せるかを先に判断する。
3. 同じ型の全画面を検索し、影響範囲を確認する。
4. この文書または対応するデザインルールへ原因と防止策を追記する。

これにより、ユーザーが「少し右」「少し上」と指示し続けなくても、配置の正確さを実装側の責務にする。

## 8. スクロールの共通契約（2026-08-09）

- **ホーム画面のネイティブなスクロール感を、すべての縦長画面の基準にする。**
- 縦方向にスクロールできる要素は `body` だけにする。画面ごとの `overflow: auto` / `overflow: scroll` は作らない。
- 内容が画面高を超えない画面は、同じ仕組みのまま自然に静止する。固定画面のために別のスクロールコンテナを作らない。
- ドット背景は `html` / `body` / app root の共通背景とし、引っ張り時にも別色・暗色・途切れた背景を露出させない。
- スクロール感を変える修正は、ホーム・長い入力画面・最終行のホーム復帰ボタンまでを実機幅で確認してから広げる。

## 9. 修正指示の記録契約（2026-08-09）

- ユーザーからの修正指示は、実装より先にこの文書または対象のデザイン文書へ記録する。
- 記録には「対象」「意図」「共通化できる範囲」「確認方法」を含める。単なる座標調整として終わらせない。
- 実装前に同型の部品を検索し、影響範囲を確認する。公開前には記録した要求をチェックリストとして照合する。

## 10. 保留の設計：交通費（電車賃）

- 電車賃は支出の**カテゴリー「交通費」**として記録できるようにする。
- 支払い方法は交通系IC・現金・カード・PayPayなど、実際の支払い元を別に残す。これにより、用途と支払い方法の両方を分析できる。
- 定期券・チャージ・単発乗車をどう集計・表示するかは、利用の仕方を確認してから次回決める。現時点では既存データを変換しない。

## 11. 確認ページを先に開く運用（2026-08-09）

- UIの修正後は、実装・公開の前に**ブラウザで操作できる確認ページを開いて見せる**。コード本文や低解像度のスクリーンショットだけで確認を依頼しない。
- ユーザーの承認を得た一画面を基準として横展開する。見た目の差が出やすいPWA本体は、同じCSSと同じ表示幅で確認し、ローカルの承認ページとの差分を確認してから公開する。
- 画面を見せる依頼を受けたら、対象ページを可視化した状態で開いたままにする。必要な場合を除き、確認ページを勝手に再読み込み・切り替えない。

## 12. ショートカットの受信先設定：404の再発防止（2026-08-09）

- 「URLの内容を取得」のヘッダは、左側の**キー**と右側の**値**を必ず分けて入力する。`Authorization: Bearer ...` を値欄だけに貼り付けてキーを空欄にすると、認証が送られず非公開Gistは404になる。
- 正しい2行は、`Authorization` → `Bearer ghp_...`、`Content-Type` → `application/json`。トークンは文書・チャット・スクリーンショットへ記録しない。
- JSON本文も1つのキー欄へ貼り付けない。`files` → `inbox.txt` → `content` の入れ子フィールドとして作る。
- 実行結果にGistのJSONが返ることは成功応答である。`files.inbox.txt.content` が送信した `kenko|...` へ更新されたかで、書き込み成功を確認する。

## 13. ヘルスケア受信書式の訂正（2026-08-09）

- 受信書式は `kenko|日付|歩数|就寝時刻|起床時刻`。睡眠時間を分数で直接渡す書式ではない。
- 例：`kenko|2026-08-09|1234|23:30|06:00`。日付は起床した日を指定し、アプリは日付またぎを考慮して睡眠時間を算出する。
- `kenko|日付|歩数|390|` のように分数だけを4列目へ入れると、就寝時刻として解釈され、睡眠が表示されない。案内する前に `applyHealthLine()` の実装とデータモデルを必ず照合する。

## 14. 自動取り込み後の画面下書き（2026-08-09）

- 自動取り込みは保存済みの健康記録へ反映した直後、画面に残っている未保存の健康入力下書きを破棄する。下書きが古い空値を持つと、受信済みの就寝・起床時刻を画面上だけで隠してしまうため。
- 受信結果は「Gistの内容が `-` へ戻ったか」だけではなく、アプリの当日表示（歩数・睡眠）まで確認する。取り込み処理と表示用下書きの状態を混同しない。

## 15. ヘルスケア受信と端末同期の直列化（2026-08-09）

- 端末データ同期はアプリ全体を置き換えるため、ヘルスケア受信と同時に実行してはならない。
- 手動更新・アプリ復帰時は、**端末データ同期 → ヘルスケア受信** の順に必ず直列実行する。
- ヘルスケア受信が成功したら、遅延保存ではなく即時保存し、その後に端末データ同期へ送信する。
- Gist が `-` になっているのに睡眠表示がない場合は、受信書式ではなく、この競合・保存順を最優先で検査する。
