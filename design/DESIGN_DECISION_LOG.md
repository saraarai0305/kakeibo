# くらしのしるし｜設計判断ログ

この文書は、利用中のフィードバック、失敗、提案、修正判断を残すための記録です。
同じ指摘を繰り返さないため、各項目に「原因」「決定」「再発防止」を必ず記します。

> このログは時系列の受付簿です。判断が共通ルールまたは画面仕様として定着したら、`README.md` にある該当の正本にも反映します。

## 運用ルール

1. 利用者から提案・違和感・修正依頼を受けたら、実装前にこのログへ記録する。
2. 見た目の調整でも、先に情報構造・操作の影響度・誤操作時の損失を確認する。
3. 修正後は、実際に表示される画面で確認し、決定した共通ルールに反映されているかを確認する。
4. 再発した場合は、以前の対策が不足した理由も追記する。単に数値だけを変更して終わらせない。

## 2026-08-12｜記録先を先に探索し、重複する箱を作らない

### 利用者提案

修正や提案を記録するときは、他の文書も確認する。すでに同じ目的の記録場所があるのに新しい箱を作り、後から整理・統合する手間を発生させない。

### 原因

設計資料は、判断ログ、操作設計票、共通規則、画面仕様、外部手順、履歴メモに役割が分かれている。記録前の探索を手順として明文化していないと、同じテーマの別ファイルや別セクションを作り、現行正本と履歴が分散する。

### 決定・再発防止

1. 記録前に `design/`、`docs/`、必要な `private/` をキーワード、画面名、操作名、設計ID、版で検索する。
2. 既存の記録を「現行正本」「判断ログ」「操作設計票」「外部手順」「履歴」に分類する。
3. 同じ目的の箱がある場合は新規ファイル・新規IDを作らず、既存の箱へ追記する。判断は判断ログ、操作の合格条件は既存の操作設計票、共通規則は共通正本へ反映する。
4. 別の箱が必要なのは、対象・責務・保存期間・公開範囲のいずれかが明確に異なる場合だけとする。その場合も、入口の索引と関連文書へのリンクを同時に追加する。
5. 記録後に同じキーワードで再検索し、同じ内容の重複箱が増えていないことを確認する。

### 実施結果

- [x] 既存の `design/README.md`、判断ログ、操作設計票、共通規則、画面仕様、`docs/README.md` を確認した。
- [x] 新しい記録ファイルは作らず、既存の記録先選定ルールへ反映する。
- [x] 今後の記録先と新規箱を作る例外条件を、HANDOFFと設計入口にも反映する。

## 2026-08-12｜共通レンダー入口の単一化と位置保持の再確認

### 実装前の判断

監査で、再描画関数に設定表示用のラッパーが重なり、位置保持の引数を将来の修正で落としやすい構造が残っていた。これは日報の保存・体調分析の指標切替・自由ボードの操作で、同じ画面位置保持契約が画面ごとに分岐する原因になる。

### 原因

`newAppRender()` の基本描画と設定画面の表示補正が別ラッパーに分かれていた。さらに、スマホブラウザは日付入力へフォーカスすると、`focusin` より先に入力欄を画面上へ移動する場合があるため、選択前の位置を個別イベントだけで記録すると再発余地があった。

### 決定・再発防止

- `renderV2(options)` を唯一の描画入口とし、通常の再描画は位置を保持、ページ遷移だけ `preserveScroll:false` を明示する。
- 設定画面の同期状態補正を共通入口へ統合し、後段ラッパーを廃止する。検査で `window.newAppRender` が1箇所、旧ラッパーが0箇所であることを確認する。
- 日付入力のブラウザ管理スクロールに備え、短い位置履歴を保持する。ただし実機で入力欄を選べる状態のタップを正本とし、単なるコード文字列検査では合格にしない。
- 日報の実作業時間は `workLogMinutes()` のみを計算正本とし、入力中・保存済みサマリー・体調分析で同じ値を使う。

### 実表示の合格条件と結果

- [x] `tools/check.ps1` で `09:00`・`18:00`・休憩`60`を入力し、「8時間0分」を確認した。
- [x] 体調分析に「実作業時間」「休憩時間」が表示され、390px幅で見えている指標をタップしてもスクロール位置が`120px`のまま保持された。
- [x] Codexのローカル390px幅で日付中央、時刻列中央、日報テンプレートの余白を目視確認し、PC幅でも再確認した。
- [x] 実ブラウザ検査でコンソールエラーなし、主要画面遷移、PWA資産版、単一レンダー入口を確認した。
- [ ] 実機Safari、保存・削除・フリーボードを含む全画面の位置保持は次段階の合格条件として残す。

## 2026-08-12｜時間割と仕事の記録を共通の仕事カタログへ統合

### 利用者提案

「一日の流れ」の仕事の時間割と「仕事の記録」を連動させる。仕事内容と優先順位などで分類できる仕事を時間割から追加し、追加済みの仕事を日報のプロジェクト／作業ドロップダウンから選べるようにする。既存の日報のプロジェクト・作業チェック欄は不要なので廃止する。日報テンプレートは、提示された仕事管理表のように、状況・やること・試行／メモ・納品／成果物・次回を残せる形へ整理する。

### 原因

現状は、時間割が `S.plan[日付]` の自由テキスト、日報が `S.workLogs[日付].project` の自由テキストと `checks` の配列に分かれている。同じ仕事を入力しても同一性を判定できず、優先順位・状態・プロジェクトを再入力する必要があるため、管理が二重になっていた。

### 決定・再発防止

- 既存の設計箱を使い、仕事の管理単位を `S.workProjects`（プロジェクト）と `S.workItems`（仕事内容）へ固定する。仕事にはプロジェクト、優先順位、状態、色、メモを持たせる。

- 仕事の記録は自由入力を正本にせず、プロジェクトと仕事内容を既存カタログから選ぶ。時間割に登録した開始・終了は候補の予定時間として日報へ提示するが、実績時間は日報側で別に記録する。
- 既存の `S.areas` と古い `project` 文字列は削除せず、初回正規化時にプロジェクト候補・表示値へ移行できるようにする。
- プロジェクト作業チェック欄は削除し、チェックを保存しない。既存の `checks` は読み込み時に破棄せず、互換用データとして残すが現行画面では使わない。
- 仕事の優先順位と状態は、仕事の追加時に設定し、時間割・日報の候補・保存済みサマリーで同じラベルを表示する。状態は未着手／進行中／待ち／完了、優先順位はA〜Dで統一する。

## 2026-08-12｜仕事の記録：作業時刻の整列と休憩控除後の実作業時間

### 利用者フィードバック

スマホ版で「作業開始」と「作業終了」の時刻表示がずれて見える。休憩時間を作業時間から引いた実作業時間も、その場で見えるようにしたい。スマホ表示で同じ問題を再発させない設計を求められた。

### 原因

作業開始・終了はネイティブの `input[type=time]` に時刻表示を任せており、日付だけを中央表示する補助表示と構造がそろっていなかった。そのため、スマホブラウザの内部部品が時刻を左寄せで描画し、2列のラベル／枠の視覚的な中心と一致しなかった。また、保存後や分析では `workLogMinutes()` が休憩を控除していたが、入力途中の画面には控除後の値を表示する派生表示がなく、利用者が実作業時間を確認できなかった。

### 決定・再発防止

- 日付・作業開始・作業終了は、実入力を維持したまま、同じ中央表示用のラッパーと `number` トークンを使う。入力欄は等幅2列の `grid` で計測し、ラベル・値・枠の中心を同じX軸に置く。
- 実作業時間は「終了−開始−休憩」で算出し、保存済みサマリー、体調分析、入力中の表示で同じ `workLogMinutes()` を使う。計算結果を別保存して不整合を作らない。
- 開始・終了が未入力のときは「未計算」、休憩が作業時間を超えるときはエラー状態を表示し、負の実作業時間を表示しない。
- 390px幅とPC幅の実表示で、2列の各ラベル・値・枠の中心座標、実作業時間の計算、休憩超過の拒否を確認する。単一ブラウザの見た目だけで合格にしない。

### 実表示の合格条件

- [x] 390px幅で作業開始・作業終了の値が各入力枠の中央に揃い、ラベルと値の中心が列中心と一致する。
- [x] 開始09:00、終了18:00、休憩60分で「実作業時間 8時間00分」と表示される。
- [x] 開始・終了未入力は「未計算」、休憩超過はエラー状態になり、保存されない。
- [x] 保存済みサマリーと体調分析の作業指標が同じ控除後計算 `workLogMinutes()` を使うことを確認した。
- [x] 実操作後も画面位置を失わず、ゴシック・数字の縦横比1:1・コンソールエラーなしを確認する。

### 実表示確認結果（2026-08-12）

- [x] Codexのローカル確認ページで変更前後を開き、390px幅・PC幅を実表示で確認した。
- [x] 390px幅の各時刻値と入力枠の中心差分は0px、PC幅も中心差分0pxだった。
- [x] 実際に09:00／18:00／休憩60分を入力し、実作業時間8時間0分を確認した。

## 2026-08-12｜仕事の記録：日付の中央揃えと日報テンプレートの余白

### 利用者フィードバック

スマホ版の仕事の記録で、日付入力の値が枠内で中央に見えない。また、「実装内容」の入力枠と次の「品質改善」ラベルの間隔が近く感じる。確認版はCodex上でページを開き、実際に操作して確認したい。

### 原因

日付はネイティブの `input[type=date]` 内部部品が表示を担うため、通常の `text-align` だけではブラウザごとの値・カレンダーアイコンの配置を統一できない。テンプレートは各入力を同じ `gap` で積んでいるが、長文入力欄の後に次の項目へ移る余白としては不足している。

### 決定・再発防止

- 日付は入力要素そのものの標準表示に任せず、値の表示を共通トークンで中央揃えできる構造にする。日付選択操作は既存の実入力を維持し、見た目だけを分離しない。
- 日付・時刻・数値は `number` トークンと `grid/flex` の中央揃えを使い、ブラウザ標準の内部部品に依存した位置調整をしない。
- 日報テンプレートは入力欄の下端から次のラベルまでの余白を共通トークン化し、長文欄でもラベルと枠が接近しないようにする。
- Codexの確認ページを変更前後に開き、スマホ幅で実表示・実操作・コンソールを確認する。コード文字列や画像だけで合格にしない。

### 実表示の合格条件

- [x] 390px幅で日付の値が入力枠の水平方向中央に見える。日付選択操作と保存対象の日付は変わらない。
- [x] 「実装内容」の枠と「品質改善」のラベルが視覚的に離れ、入力欄の境界と次の見出しが接触しない。
- [x] Codexで開いたローカル確認ページ上で、日付変更・入力・無効な保存検証を実操作できる。
- [x] 画面位置保持、ゴシック書体、数字の縦横比1:1、PC幅と390px幅、コンソールエラーなしを確認する。

## 2026-08-11｜設定操作は「配置」より先に影響度で整理する

### きっかけ

デザイン設定センターで「設定を保存」「初期設定に戻す」「設定を書き出す」「設定を読み込む」を横並びにし、幅不足で「設定を読み込む」だけが折り返された。

### 根本原因

ボタンを先に同列の要素として扱い、各操作の目的・可逆性・誤操作時の損失を整理しないまま、整列と余白だけで解決しようとした。

### 決定した情報構造

| 操作 | 役割 | 影響度 | 表示上の扱い |
| --- | --- | --- | --- |
| 設定を保存 | 現在の設定を確定する | 低い・日常操作 | 主操作として独立表示 |
| 設定を書き出す | 設定の控えを作る | 低い・安全 | 「設定の入出力」グループ |
| 設定を読み込む | 保存済み設定を反映する | 中程度・上書きの可能性 | 「設定の入出力」グループ、実行前に確認 |
| 初期設定に戻す | 現在の調整を失う | 高い・破壊的 | 保存から離し、詳細操作／初期化として隔離、確認必須 |

### 実装の順序

1. 情報と操作を、役割・影響度・可逆性で分類する。
2. 誤操作時の損失が大きい操作を隔離または段階表示にする。
3. 同じ役割・近い重さの操作だけを並列にする。
4. 最後に、枠・中央揃え・余白・横並び／縦並びを決める。

### 再発防止チェック

- [ ] 先に「何をする操作か」を文章で定義したか。
- [ ] 誤操作で失われるものを確認したか。
- [ ] 破壊的・上書き操作を主操作の隣に置いていないか。
- [ ] 並列配置は、意味と影響度が近い操作に限定されているか。
- [ ] レイアウトは情報構造の決定後に検討したか。

## 2026-08-11｜設定センターは操作書体と紙面書体を分離する

### 問題

設定センターの見出しが明朝体になっていた。これは「機能画面はゴシックで統一する」という共通規則と矛盾する。

### 原因

紙面装飾用の `display` 書体トークンを、設定センターの `h1` とプレビュー見出しへ直接適用していた。`display` を「見出し全般」と誤って扱い、用途別の書体分類がコードに反映されていなかった。

### 決定

1. 設定・フォーム・操作・機能画面の見出し・金額は UI ゴシックを使用する。
2. 明朝系は、装飾的なロゴか、利用者がフリーボードで選ぶ表現用途に限定する。
3. `display` トークンを使う場合は、紙面装飾である理由を仕様へ明記する。
4. デザイン設定の変更は即時にプレビューするが、端末への確定保存は `設定を保存` のみで行う。

### 再発防止

- [ ] コンポーネントに書体を指定する前に、`操作 / 情報 / 装飾 / 利用者コンテンツ` のどれかを判定する。
- [ ] 画面実装前に、影響度で操作をグループ化してからレイアウトを決める。
- [ ] 設定センターは保存・入出力・初期化の3群が視覚的に分かれているか、実表示で確認する。

## 2026-08-11｜危険操作の「入口」と「実行」を同じ枠にしない

### 再発した問題

初期設定に戻す操作を折りたたみにはしたが、破線の大きな外枠全体が初期化の操作範囲に見えた。危険操作を通常操作と同じ部品として扱ったため、説明を開く行と実行範囲が混同された。

### 根本原因

## 2026-08-12｜仕事ログの複数プロジェクト記録と共通時刻軸

### 利用者フィードバック

一日に複数の仕事を同時並行で進めるため、「仕事を選ぶ」は複数プロジェクトを選択でき、各プロジェクトの仕事内容を記録できるようにする。日報テンプレートは利用者向けの名称「仕事の内容」に変更し、やったこと・成果・今の状況などは定型選択と自由入力を併用する。PCでは正しく見えてもスマホで日付・時間割・予定編集の時刻がずれるため、表示計算とネイティブ日付・時刻入力の見せ方を共通化する。

### 原因

- 仕事ログが単一の `projectId`／`workItemId` だけを保存する構造で、同時並行の仕事を一つの記録に保持できない。
- 日報本文が自由記述だけで、状態や成果の分類が一覧・分析へつながりにくい。
- 時間割のJavaScript計算が1時間28px、CSSの目盛りが1時間49pxで別々に定義され、ブラウザ幅や実表示でラベル・カード・罫線がずれる余地がある。
- `input[type=date/time]` のネイティブ内部描画をそのまま表示しており、Safariの内部余白・アイコン・文字基線差を吸収できていない。

### 判断・再発防止

1. 複数プロジェクトは配列で正本化し、旧単一IDも互換用に残す。各プロジェクトに仕事内容のドロップダウンを持たせ、既存保存データと未選択状態を壊さない。
2. 仕事の内容は定型選択を基本にし、選択肢にない内容だけ自由入力へ切り替える。保存時は既存の `done` などの項目名を維持して、履歴・分析との整合性を保つ。
3. 時間割の1時間高さを共通トークン `FLOW_HOUR_PX` とCSS変数で一元化し、ラベル・予定カード・現在線・背景罫線が同じ軸を使う。カードは表示領域内で幅をクランプする。
4. 日付・時刻は実入力を透明な操作層、表示文字を共通の中央表示層に分ける。Safari固有の内部描画を見せず、フォーカス時も入力枠と操作性を維持する。
5. 保存・日付変更・選択後は同じページとスクロール位置を保持し、危険操作（削除）は保存から分離する。

### 実表示での合格条件

- 390px相当とPC幅で、複数プロジェクトを選択し、それぞれの仕事内容を選んで保存・再表示できる。既存の単一プロジェクト記録も表示される。
- 「仕事の内容」が画面上の利用者向け見出しになり、成果・状況・次の作業などを選択式で入力でき、自由入力へ切り替えても既存値が失われない。
- 390px相当とPC幅で、時間割の時刻ラベル・背景罫線・予定カード・現在線が同じ1時間軸に揃い、予定カードが左右・上下の枠外へ出ない。
- 390px相当とPC幅で、仕事ログ・体調記録・予定編集の日付／開始／終了が中央表示され、Safariの表示差で文字やアイコンがずれない。
- 画面操作後も選択した日付・スクロール位置を失わず、コンソールエラーがない。
