# 根幹改善フェーズ — 提案書

作成日: 2026-08-11
対象: くらしのしるし PWA 全画面 / 自由ボード / 体調分析 / 共通UI

## 0. このフェーズの目的

個別画面をその場で微調整する段階を止め、**生活の基盤をこれ一つで支える**ための土台を作り直す。

優先順位は次の通り。

1. 画面の中心・余白・文字・アイコンが再びずれない共通基盤を作る。
2. 自由ボードを「自由に置ける」「整理できる」「後から見返せる」道具にする。
3. 分析を、数値の羅列ではなく、生活の意思決定に使える情報へ変える。
4. 端末データ、画像、アイコン、同期データを壊さず拡張できる保存構造にする。

このフェーズ中は、土台に依存する見た目の横展開・公開を急がない。各基盤を実表示で承認してから、次へ進む。

## 1. 現状監査と根本原因

### 1-1. 中心がずれ続けた主因

これは「デザイン規則がない」ことだけが原因ではない。規則を実装へ一貫して適用できない構造が原因である。

| 確認結果 | 影響 |
| --- | --- |
| `ui-v2.js`、`ui-paper-baseline.css`、`ui-analog.css` の3系統が同じ画面を重ねて装飾している | 片方で直した余白・フォント・高さを別のCSSが上書きする |
| `!important` が `ui-paper-baseline.css` に412件、`ui-analog.css` に105件ある | 部品ごとの正しい指定より、後から足した例外が優先される |
| 画面固有の `top`、`margin`、文字記号に依存した補正がある | フォント、文字数、iPhoneの描画差で見た目が動く |
| 戻る・設定・ホームへ戻る等の同種部品が別々に実装されている | 同じ役割なのに、中心・文字サイズ・余白が画面ごとに違う |
| 規則文書に48px / 44px / 56pxなど複数の基準が残っている | 実装者がどれを正とすべきか判断できない |

**結論:** 以後は「文字を何px下げる」という修正を正解にしない。部品そのものを、箱の中心を基準に配置する設計へ置き換える。

### 1-2. 再発防止の実装原則

- 枠内の単体要素は `grid` の `place-items: center` を標準にする。
- アイコンと文字が並ぶ操作は `inline-flex` + `align-items: center` + 明示的な `gap` を使う。基線や余白で中央を推測しない。
- ヘッダーは `minmax(56px, 1fr) auto minmax(56px, 1fr)` の3列とし、左右の有無に関係なく中央タイトルを物理的に中央へ置く。
- `×`、`¥`、矢印などの文字記号は操作アイコンに使わない。24×24の正規化SVGをアイコン一覧から呼び出す。
- 数字は `font-variant-numeric: lining-nums tabular-nums`。金額、日付、時刻は同じ数値書式にする。
- 基本文字は縦横比1:1を崩さない。強調は太さ・色・周囲余白で行い、字幅圧縮や縦横拡大を使わない。
- `!important` を新規追加しない。既存のものは部品移行時に削減する。

CSS Box Alignment はGrid/Flexで水平方向・垂直方向の一貫した配置を扱う標準であり、このアプリの「枠の中心を取る」契約に採用する。
参照: [MDN CSS Box Alignment overview](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Box_alignment/Overview)

## 2. 新しいデザインシステム

### 2-1. 一つの正本と部品の契約

次の4層へ分割する。画面は部品を組み合わせるだけにし、画面固有の位置調整を禁止する。

| 層 | 内容 | 例 |
| --- | --- | --- |
| Tokens | 色、余白、角丸、文字、影、操作高さ | `--space-12`、`--radius-panel`、`--text-meta` |
| Primitives | 最小部品 | `Icon`、`IconButton`、`Stack`、`Divider` |
| Components | 再利用する意味ある部品 | `PageHeader`、`Masthead`、`ReturnHome`、`Metric`、`SegmentControl` |
| Screens | 画面の組立 | 支出・収入、時間割、体調分析、自由ボード |

### 2-2. 固定する数値

| 項目 | 基準 |
| --- | --- |
| 画面左右余白 | 24px |
| 通常の縦間隔 | 8 / 12 / 16 / 24 / 32px のみ |
| アイコン | SVG 24px。見出し横のみ28px。座布団は部品ごとに固定 |
| 主ボタン | 高さ56px、本文16px以上 |
| 補助ボタン | 高さ44px、本文14px以上 |
| ラベル / 日付 / 版数 | 同一のメタ書式。サイズ・太さ・字間を共通化 |
| 主見出し | 日本語は1画面1つ、最大30px。英字ラベルは15px |
| 数字 | UI用ゴシック、等幅数字、変形なし |

### 2-3. 書体の方針

- 主見出しだけを明朝系、操作・本文・数値はゴシック系にする。
- PCに入っているフォントはiPhoneに必ず存在するとは限らない。PWAでは、利用許諾があるフォントをWOFF2として同梱するか、Apple/Windows双方にあるフォールバックを明示する。
- 「等幅」は各文字が同じ横幅という意味。本文に強制しない。金額・時刻には**等幅数字**だけを使い、桁揃えを安定させる。

## 3. 自由ボードを Notion × Freeform × マインドマップへ拡張する案

### 3-1. 三つの見方、データは一つ

同じアイデアを複製して三種類に保存しない。一つのボードデータに、次の三つの表示を用意する。

| 表示 | 得意なこと | 使う場面 |
| --- | --- | --- |
| キャンバス | 配置、画像、手書き、構図、自由な関連付け | 映像案、プラグイン案、人生設計の発散 |
| アウトライン | 折りたたみ、検索、タグ、チェック、優先順位 | 文章の整理、やることへの変換、見返し |
| マップ | 親子・関連線・枝の折りたたみ | 中心テーマから考えを広げる、構造を把握 |

Notionのブロックは種類を変換して情報の見方を変えられるため、このアプリでも「テキスト・メモ・チェック・画像」を同じノードとして扱う方針に合う。
参照: [Notion Help — What is a block?](https://www.notion.com/help/what-is-a-block)

### 3-2. ノードモデル

```text
Board
  ├─ viewport { x, y, zoom }
  ├─ nodes[]  { id, type, x, y, w, h, z, parentId, style, content, properties }
  ├─ edges[]  { id, fromId, toId, label, style }
  ├─ groups[] { id, title, nodeIds, collapsed }
  └─ history  { undo[], redo[] }
```

- `parentId` がツリー構造を作る。
- `edges` は「親子ではない関連」をつなぐ。
- `groups` は複数項目をフレームにまとめ、折りたためる。
- Canvas / Outline / Map は上記の同じデータを読むだけにする。
- 画像・手書き・テキストはノード種別であり、別アプリのように分断しない。

### 3-3. 操作の優先順位

1. タップ: 選択、もう一度タップ: 操作メニュー
2. ダブルタップ: テキスト編集
3. 長押し/右クリック: 削除・複製・グループ化
4. 空白ドラッグ: 範囲選択、二本指: キャンバスの移動・拡大縮小
5. マップ表示: ノード選択 → 「子を追加」「関連をつなぐ」

選択中の破線、ハンドル、削除操作は**選択時だけ**表示する。常時は紙面の装飾と混同しないようにする。

モバイルとPCの操作を別々に実装するのでなく、Pointer Eventsを中心に統一し、入力装置ごとの違いはジェスチャー解釈だけに限定する。Pointer Eventsはマウス、ペン、タッチを同じ座標モデルで扱える。
参照: [MDN Pointer Events](https://developer.mozilla.org/en-US/docs/Web/API/Pointer_events/Using_Pointer_Events)

### 3-4. 実装段階

| 段階 | 実装 | 完了条件 |
| --- | --- | --- |
| FB-1 | 専用store、選択・履歴・ズーム・パンの分離 | 操作してもページ先頭へ飛ばない |
| FB-2 | テキスト/図形/画像/手書きの共通ノード | 選択枠・ハンドル・削除が全種別で一貫 |
| FB-3 | アウトラインと親子構造 | ツリーで折りたたみ・並べ替え可能 |
| FB-4 | マップ、関連線、自動レイアウト | ノードから子・関連を追加できる |
| FB-5 | 複数選択、複製、グループ、検索・タグ | ボードが大きくなっても整理できる |

## 4. 分析を「生活のための意思決定」にする案

### 4-1. 画面構造

分析は「たくさん表示する」のでなく、次の3つの問いに答える。

| 画面 | 答える問い | 主なデータ |
| --- | --- | --- |
| 今週の状態 | 今週、生活の土台はどうだったか | 睡眠、歩数、こころ、からだ、毎日の習慣 |
| 習慣とコンディション | 自分では何が関係していそうか | 同日・翌日の比較、データ欠損、個人平均との差 |
| お金と予定 | お金と時間をどこへ使ったか | 支出/収入、支払方法、予定、固定費 |

### 4-2. 体調比較グラフ

- 横軸は曜日/日付で共通。
- **睡眠と歩数だけ棒グラフ**。同じ日付位置に重ねてよいが、透明度・幅・色を変える。
- **からだ・こころ・毎日の習慣は折れ線**。丸/四角/三角などの点形状と線種を分ける。
- 個別の縦軸を可視化せず、詳細は点/線をタップ・ホバーして対応色の小さなツールチップにする。
- 欠損日は値を捏造しない。線は見た目の連続性のため結んでも、ツールチップでは「未記録」と明示する。
- 重なった箇所は連続タップで候補を巡回する。
- 二本指で拡大でき、詳細表示にはアニメーションを入れない。

### 4-3. 振り返りの出力

1. 事実: 平均睡眠、平均歩数、記録日数、習慣達成率。
2. 個人内の傾向: 「睡眠が自分の中央値より短い日のこころ」「歩数が自分の中央値より多い日のからだ」など。
3. 行動候補: 強制でなく、次週に一つだけ試す小さな提案。
4. 信頼度: データ日数と欠損を表示し、少ないときは結論を出さない。

研究上、日々の活動量と気分には個人内の関連が報告される一方、方向や大きさは人・文脈で変わる。したがって、このアプリは診断や因果断定ではなく、**本人の生活内で再現する傾向**を示す。
参照: [日常の身体活動と感情の個人内関連の系統的レビュー](https://pubmed.ncbi.nlm.nih.gov/41316836/)、[睡眠の質と翌日の気分の個人内関連](https://pubmed.ncbi.nlm.nih.gov/30916663/)

### 4-4. AI分析の扱い

- 公開PWAにOpenAI APIキーを置かない。
- 実装する場合は、本人が送信に同意した集計データだけをサーバー側へ送る。
- 結果形式は `タイトル / 根拠となる期間 / 傾向 / 限界 / 次に試す一つ` に固定する。
- 医療的な診断、治療助言、断定はしない。

## 5. 保存形式・アイコン・画像の判断

| 対象 | 正しい保存先 | 理由 |
| --- | --- | --- |
| アイコン | SVGの中央レジストリ | 軽量、拡大しても荒れず、線幅・色を統一できる |
| 紙の質感・写真 | WebP/PNG | ラスター表現が必要なものだけに限定 |
| 自由ボードの構造 | JSON schema + IndexedDB | ノード、関連線、履歴を構造として扱える |
| 自由ボードの画像・手書き | IndexedDBのBlob、ノードには参照ID | localStorageを肥大化させない |
| 歩数・睡眠の受信箱 | 現行Gistの短いテキスト | iPhoneショートカットとの互換を維持 |
| 表形式のエクスポート | CSV | 分析結果を外部で見る用途に限定 |

CSVはアイコンや自由ボードの関係・装飾・画像を表せないため、UIの正本には使わない。IndexedDBは構造化データとファイル/Blobのクライアント保存に向く。
参照: [MDN IndexedDB API](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API)

アイコンには次を新設する。

- `iconRegistry`: 名称、用途、24×24 viewBox、線幅、使用ページを一元管理。
- `Icon`: SVGを1つの共通部品で描画。画面ごとにパスを複製しない。
- `assetRegistry`: 画像のMIME type、サイズ、圧縮後サイズ、参照数を記録。
- PWA同梱フォントはライセンスと容量を確認し、未同梱のPCローカルフォントには依存しない。

## 6. 実装順と品質ゲート

| 順序 | 作業 | 承認条件 |
| --- | --- | --- |
| 1 | CSSの3層を設計トークン/共通部品へ移行する計画を作り、重複部品を棚卸し | 画面ごとの上書き表が完成 |
| 2 | `PageHeader`、`Masthead`、`ReturnHome`、`IconButton`を新部品で実装 | 390×844 / 393×852の実表示で中心を確認 |
| 3 | アイコンレジストリとSVG統一 | 既存全アイコンの用途と見た目を一覧で確認 |
| 4 | 支出・収入ページを新基盤で再実装 | 承認済み基準ページと比較して一致 |
| 5 | 自由ボードFB-1〜FB-2 | パン・ズーム・選択・削除・保存の実機確認 |
| 6 | 分析の新グラフと振り返り | 同日比較・欠損・重なりタップを実データで確認 |
| 7 | アウトライン/マップ、AI分析は別の段階で追加 | 同意・保存・安全性を確認 |

### 必須の確認ルール

- 実装前: 変更対象の**実表示確認ページ**をブラウザで開く。
- 実装後: 同じページを実表示で確認し、PCとiPhoneの両方で必要な画面を確認する。
- スクリーンショットやコードだけで「確認済み」にしない。
- 公開前: `tools/check.ps1`、データ維持、画面遷移、コンソールエラー、モバイル表示を確認する。
- 変更要求は、この設計フォルダへ「意図 / 原因 / 対応 / 再発防止」として先に記録する。

## 7. 次の意思決定

この提案を承認後、最初に実装するのは **順序1〜3（共通基盤・ヘッダー・アイコン）** とする。

自由ボードと分析はこの基盤の上に載せる。これにより、同じ中心ずれ・画面固有の調整・アイコン差し替え漏れを繰り返さない。

## 変更履歴

### 2026-08-11 — 根幹改善フェーズを開始

- CSSの多層上書きと `!important` 集中を、中心ずれの根本原因として記録した。
- 画面個別の微調整から、トークン・共通部品・実表示承認を先に行う工程へ切り替えた。
- 自由ボードを Canvas / Outline / Map の同一データ3ビューにする方針を追加した。
- 分析を「事実 → 個人内の傾向 → 一つの行動候補 → 信頼度」で出す方針を追加した。
