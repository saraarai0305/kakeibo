# 同期の役割分離

## 固定する構造

| 役割 | 保存先 | 扱うデータ |
| --- | --- | --- |
| 端末データ同期 | `mainichi.sync` / `mainichi-data.json` | PC・iPhone間のアプリ記録全体 |
| ヘルスケア自動取り込み | `mainichi.health-sync` / `inbox.txt` | iPhoneショートカットの歩数・睡眠だけ |

この2つは **別のGist ID** を使う。同じGistに統合しない。

## 理由

- ショートカットは `inbox.txt` だけをPATCHする。
- 端末データ同期はアプリ全体を保存するため、ショートカットの失敗や設定ミスと混在させない。
- 「同期済み」は設定値が入っているだけで表示しない。実際にGitHubへ接続できたときのみ「接続確認済み」とする。

## 設定UIの原則

1. 「端末データ同期」と「ヘルスケア自動取り込み」は別フォルダ・別ステータスにする。
2. ヘルスケア側には、ショートカットの送信先URLと本文形式を明示する。
3. ヘルスケア受信の失敗は、端末データ同期の失敗として表示しない。
4. 既存データを初期化・上書きしない。

### iPhone正本からPCへ共有する場合の固定順序（2026-08-12）

- iPhoneを正本にし、PCは「読み取り専用（受信のみ）」で既存の端末データ用Gistへ参加する。
- 未設定のPCで読み取り専用を選んだ場合、既存Gist IDがない限り新規Gistを作成しない。新規作成は、明示的に記録・送信する端末を作る場合だけ許可する。
- PC側の同期開始前に、PCのローカル記録を退避する。既存Gistの受信で置き換わるのはPC側だけであり、受信処理はiPhone側GistをPATCHしない。
- 順序は「iPhone側の既存同期先確認 → PC側バックアップ → PCでトークン・既存Gist ID入力 → PCを読み取り専用に設定 → 既存内容へ合わせる確認 → 受信 → PCの状態・表示確認」とする。
- トークン、Gist ID、認証URLは文書・チャット・ログへ再掲しない。値ではなく、受信内容・更新時刻・画面反映で確認する。
- 読み取り専用の状態から記録・送信可能へ戻す操作は、端末データ同期の設定内で明示確認を通す。ヘルスケア自動取り込みの役割とは混ぜない。

## 変更時の確認

- ショートカット受信処理が `mainichi-data.json` に触れないこと。
- 手動更新・アプリ起動・復帰時に、端末同期とヘルスケア受信をそれぞれ実行すること。
- Gistの作成時、端末用は `mainichi-data.json` のみ、ヘルスケア用は `inbox.txt` のみであること。

## ヘルスケア自動取り込みの受信保証（2026-08-09）

### 原因

- 旧実装は、歩数だけを取り込めた時点で `inbox.txt` を `-` に戻していた。
- そのため睡眠時刻の形式が不正・未反映・端末データ同期との競合で表示されなかった場合も、再受信に必要な値まで失われていた。

### 恒久ルール

1. `inbox.txt` は使い捨ての受信箱ではなく、**最後に受信したヘルスケア値のスナップショット**として保持する。アプリ受信後に `-` へ書き戻さない。
2. 受信書式は `kenko|YYYY-MM-DD|歩数|就寝時刻|起床時刻`。睡眠は `23:30` / `06:00` のように就寝・起床を必ず両方送る。
3. 時刻は半角・全角コロンを正規化し、`00:00`〜`23:59` を検証してから保存する。片方だけ、または不正な時刻は既存睡眠値を消さない。
4. 設定画面には直近の受信結果（日付・歩数・睡眠時間）を表示する。歩数だけ受信できた状態と、睡眠まで確認できた状態を区別する。
5. ヘルスケア受信処理は端末データ同期と分離する。端末同期が後から実行されても、保持中の `inbox.txt` から再受信して復旧できること。

### 検証手順

1. ショートカット実行後、GitHub Gist の `inbox.txt` が `kenko|...` のまま残っていることを確認する。
2. アプリの「ヘルスケア自動取り込み」で「受信を確認」を押す。
3. 設定画面が「受信済み・睡眠まで確認」と、受信した日付・歩数・睡眠時間を表示することを確認する。

### 表示確認の原則

- 見た目や操作変更は、コード表示・スクリーンショットだけで完了としない。必ずローカルの実表示ページで確認してから実装・公開する。
